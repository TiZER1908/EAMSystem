# Характеристика информационной системы

## 1. Назначение системы

Корпоративная информационная система управления производственными активами (EAM-система) предназначена для автоматизации процессов учёта, технического обслуживания и ремонта оборудования на предприятии.

Система создаётся с целью замены разрозненных инструментов учёта (электронные таблицы, бумажные журналы, устные договорённости) на единое информационное пространство, в котором сосредоточена полная и актуальная информация о состоянии, истории и стоимости владения каждой единицы оборудования.

Система отвечает на ключевые вопросы эксплуатации:
- Какое оборудование имеется на предприятии?
- Где оно находится и в каком состоянии?
- Кто за него отвечает?
- Когда последний раз проводилось обслуживание?
- Какие работы предстоят в ближайшее время?
- Сколько стоит содержание каждой единицы?

## 2. Цели и задачи

**Цель:** повышение эффективности использования производственных активов за счёт создания единой корпоративной информационной системы учёта и обслуживания оборудования.

**Задачи:**
1. Сформировать единый реестр оборудования с полной историей изменений.
2. Автоматизировать процесс подачи и обработки заявок на ремонт.
3. Обеспечить планирование планово-предупредительных ремонтов (ППР).
4. Организовать учёт запасных частей и материалов, используемых при ремонтах.
5. Реализовать ролевую модель доступа для различных категорий сотрудников.
6. Обеспечить формирование отчётности по простоям, затратам и эффективности.
7. Предусмотреть интеграцию с внешними системами предприятия (мониторинг, аутентификация, ERP).

## 3. Объект и предмет

**Объект исследования:** процессы управления производственными активами на предприятии.

**Предмет исследования:** автоматизация процессов учёта, обслуживания и ремонта оборудования средствами корпоративной информационной системы.

## 4. Границы проекта

### 4.1. Что входит в проект

- Учёт оборудования (реестр, паспорт, иерархия, история).
- Управление заявками на ремонт (подача, обработка, закрытие).
- Управление нарядами (создание, назначение, выполнение).
- Справочник запасных частей (без полноценного складского учёта).
- Базовая отчётность (открытые заявки, история ремонтов, загрузка исполнителей).
- Ролевая модель доступа (4 основные роли).
- REST API для интеграции с внешними системами.
- Интеграция с сервисом мониторинга состояния кластера БД.

### 4.2. Что не входит в проект (перспективы развития)

- Полноценный складской учёт (партии, сроки годности, несколько складов).
- Финансовый учёт (амортизация, бюджетирование, расчёт TCO).
- Предиктивная аналитика на основе машинного обучения.
- Мобильное приложение (реализуется только адаптивный веб-интерфейс).
- Прямая интеграция с ERP-системами (1С, SAP).
- Интеграция с SCADA / АСУ ТП.
- Интеграция с LDAP / Active Directory (описана как архитектурная возможность).

## 5. Функциональные подсистемы

Система декомпозируется на шесть функциональных подсистем (модулей).

### 5.1. Модуль учёта активов
- Создание и редактирование карточек оборудования.
- Иерархическая структура: предприятие → цех → участок → единица оборудования.
- Атрибуты: инвентарный номер, наименование, модель, дата ввода в эксплуатацию, статус, местоположение, ответственный сотрудник.
- Ведение истории: ремонты, перемещения, изменения статуса.

### 5.2. Модуль заявок
- Подача заявки любым авторизованным сотрудником.
- Указание оборудования, описания проблемы, приоритета, возможности прикрепления фото.
- Жизненный цикл: «Новая» → «Принята» → «В работе» → «Закрыта» / «Отклонена».
- Просмотр очереди заявок мастером и назначение исполнителя.

### 5.3. Модуль нарядов
- Создание наряда мастером на основе заявки или плана ППР.
- Атрибуты: исполнитель, сроки, перечень работ, использованные запчасти.
- Просмотр и отметка о выполнении механиком.
- Закрытие наряда с записью в историю оборудования.

### 5.4. Модуль справочников
- Типы оборудования.
- Запасные части и материалы.
- Подразделения и локации.
- Пользователи и роли.

### 5.5. Модуль отчётности
- Открытые заявки и наряды.
- История ремонтов по оборудованию.
- Загрузка исполнителей (механиков).
- Простои оборудования по данным нарядов.

### 5.6. Модуль администрирования
- Управление пользователями.
- Назначение ролей.
- Настройка справочников.
- Просмотр журнала действий (аудит).

## 6. Роли пользователей

| Роль | Описание | Основные возможности |
|---|---|---|
| Администратор | Сотрудник ИТ-службы | Управление пользователями, справочниками, полный доступ ко всем данным |
| Мастер (диспетчер) | Руководитель ремонтной службы | Просмотр всех заявок, создание нарядов, назначение исполнителей, закрытие нарядов |
| Механик | Сотрудник ремонтной службы | Просмотр своих нарядов, отметка о выполнении, списание запчастей |
| Заявитель | Любой сотрудник предприятия | Подача заявок, просмотр их статуса, просмотр истории по своему оборудованию |

Дополнительно (в перспективе): роль «Руководитель» — просмотр отчётов и дашбордов без права редактирования.

## 7. Интеграции

### 7.1. Реализуемые интеграции

**Интеграция с сервисом мониторинга состояния кластера БД.**
- Тип: REST API (HTTP/JSON).
- Направление: сервис мониторинга опрашивает EAM-систему.
- Точки взаимодействия: `/actuator/health`, `/actuator/metrics`.
- Назначение: отслеживание состояния подключения к отказоустойчивому кластеру PostgreSQL, выявление аномалий, фиксация событий failover.

### 7.2. Перспективные интеграции

**Интеграция с корпоративной системой аутентификации (LDAP / Active Directory).**
- Тип: LDAP.
- Назначение: вход в систему под корпоративной учётной записью без отдельного пароля.

**Интеграция с ERP-системой (1С, SAP).**
- Тип: REST / SOAP / обмен файлами.
- Назначение: передача данных о затратах на ТОиР, закупках, контрагентах.

**Интеграция с SCADA / АСУ ТП.**
- Тип: OPC UA / MQTT.
- Назначение: получение данных с датчиков оборудования для перехода к обслуживанию по состоянию.

## 8. Архитектура (краткое описание)

Система построена по трёхзвенной клиент-серверной архитектуре:

- **Клиентский уровень:** одностраничное веб-приложение (SPA) на Vue.js. Взаимодействие с сервером через REST API.
- **Серверный уровень:** Spring Boot-приложение, реализующее бизнес-логику, REST-контроллеры, безопасность (Spring Security + JWT).
- **Уровень данных:** отказоустойчивый кластер PostgreSQL (3 узла под управлением Patroni), доступ через HAProxy.

Дополнительно:
- **Мониторинг:** Spring Boot Actuator отдаёт метрики, внешний сервис мониторинга их опрашивает.
- **Формат обмена:** JSON over HTTP.

## 10. Связь с курсовой работой

В рамках отдельной курсовой работы разрабатывается сервис наблюдения и коррекции работы отказоустойчивого кластера. Данный сервис является внешней системой по отношению к EAM-системе и взаимодействует с ней через REST API (Actuator). Это обеспечивает:

- Разделение ответственности между бизнес-логикой (EAM) и инфраструктурным мониторингом.
- Независимость развёртывания и обновления обоих компонентов.
- Возможность мониторинга состояния EAM-системы даже при её частичной деградации.
