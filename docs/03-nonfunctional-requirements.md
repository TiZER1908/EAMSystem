# Нефункциональные требования

Нефункциональные требования описывают, **как** система должна работать, в отличие от функциональных требований, которые описывают, **что** система должна делать. Они определяют качественные характеристики системы: производительность, надёжность, безопасность, удобство использования и другие.

## 1. Требования к производительности

- **Время отклика API:** не более 2 секунд для 95% запросов при нагрузке до 100 одновременных пользователей.
- **Время отклика интерфейса:** не более 3 секунд на отрисовку основных страниц (списки, карточки).
- **Пропускная способность:** система должна выдерживать не менее 50 запросов в секунду без деградации.
- **Время выполнения отчётов:** не более 5 секунд для отчётов по одному объекту, не более 30 секунд для сводных отчётов.
- **Запуск приложения:** не более 60 секунд от старта до готовности принимать запросы.
- **Работа с большими списками:** пагинация на стороне сервера, не более 50 записей на страницу по умолчанию.

## 2. Требования к надёжности и отказоустойчивости

- **Отказоустойчивость БД:** кластер PostgreSQL из трёх узлов под управлением Patroni с автоматическим выбором нового лидера при отказе текущего.
- **Время failover:** не более 30 секунд с момента отказа лидера до назначения нового.
- **Целостность данных:** потоковая репликация между узлами, нулевой лаг в нормальном режиме.
- **Доступность:** целевой показатель — 99% времени в рабочие часы (не более 7 часов простоя в год).
- **Восстановление:** возможность восстановления из резервной копии (в перспективе — автоматическое резервное копирование).
- **Обработка сбоев:** система должна корректно обрабатывать разрыв соединения с БД и автоматически переподключаться после восстановления.
- **Идемпотентность критичных операций:** повторное выполнение операции при сбое сети не должно приводить к дублированию данных.

## 3. Требования к безопасности

- **Аутентификация:** на основе JWT-токенов. Время жизни access-токена — 1 час, refresh-токена — 24 часа.
- **Хранение паролей:** bcrypt-хэширование с солью.
- **Авторизация:** ролевая модель доступа (RBAC) на уровне API и UI.
- **Защита от атак:** валидация всех входящих данных, защита от SQL-инъекций (через ORM), защита от XSS (экранирование на фронте), защита от CSRF (для форм аутентификации).
- **Аудит:** логирование всех критичных действий (создание, изменение, удаление сущностей) с указанием пользователя и времени.
- **Транспорт:** передача данных по HTTPS (в продакшене), CORS-политика для ограничения источников запросов.
- **Защита Actuator:** административные эндпоинты доступны только авторизованным пользователям с ролью ADMIN. Публичными остаются только `/actuator/health` и `/actuator/info`.
- **Ограничение попыток входа:** блокировка учётной записи после N неудачных попыток входа (в перспективе).

## 4. Требования к масштабируемости

- **Горизонтальное масштабирование backend:** приложение должно быть stateless (без хранения состояния между запросами на сервере), чтобы можно было запускать несколько экземпляров за балансировщиком.
- **Вертикальное масштабирование БД:** возможность добавления реплик для распределения нагрузки чтения.
- **Рост числа пользователей:** система должна поддерживать рост до 500 пользователей без изменения архитектуры.
- **Рост числа активов:** система должна поддерживать реестр до 10 000 единиц оборудования.
- **Рост числа заявок:** система должна поддерживать обработку до 1000 заявок в месяц.

## 5. Требования к совместимости

- **Браузеры:** Chrome, Firefox, Edge последних двух версий, Safari 15+.
- **Разрешение экрана:** от 1366×768 (минимальное) до 4K.
- **Адаптивность:** корректное отображение на планшетах (ширина от 768px), на мобильных — упрощённый интерфейс.
- **Формат обмена данными:** JSON (RFC 8259).
- **Кодировка:** UTF-8.
- **Формат даты и времени:** ISO 8601 для API, локальный формат для UI.

## 6. Требования к сопровождаемости

- **Версионирование схемы БД:** через систему миграций Flyway. Каждое изменение схемы — отдельная миграция с уникальным номером.
- **Документация API:** автоматическая генерация через SpringDoc OpenAPI (Swagger UI).
- **Логирование:** структурированные логи в формате, пригодном для машинной обработки. Уровни: ERROR, WARN, INFO, DEBUG.
- **Тестирование:** покрытие ключевых сценариев unit- и integration-тестами (целевое покрытие — не менее 60%).
- **Стиль кода:** единые соглашения для backend (Java) и frontend (TypeScript), проверка через линтеры (Checkstyle, ESLint, Prettier).
- **Документация:** вся проектная документация хранится в репозитории в формате Markdown (подход Docs-as-Code).

## 7. Требования к удобству использования (юзабилити)

- **Единый интерфейс:** все страницы построены по схеме Header + Sidebar + Content.
- **Ролевой интерфейс:** навигация и доступные действия формируются динамически в зависимости от роли пользователя.
- **Обратная связь:** все действия пользователя сопровождаются визуальным откликом (индикаторы загрузки, уведомления об успехе/ошибке).
- **Валидация форм:** проверка вводимых данных на клиенте и на сервере с понятными сообщениями об ошибках.
- **Локализация:** русский язык интерфейса, поддержка форматов даты и времени, принятых в РФ.
- **Доступность:** контрастность текста и фона соответствует WCAG 2.1 AA (в перспективе — полное соответствие).
- **Горячие клавиши:** поддержка базовых горячих клавиш для навигации (в перспективе).

## 8. Требования к мониторингу и наблюдаемости

- **Health-check:** эндпоинт `/actuator/health` для проверки работоспособности приложения и подключения к БД.
- **Метрики:** сбор метрик JVM, HTTP-запросов, пула соединений HikariCP через Micrometer.
- **Интеграция с сервисом мониторинга:** внешний сервис опрашивает метрики и отслеживает состояние кластера БД.
- **Оповещения:** фиксация событий failover, превышения лага репликации, недоступности узлов.
- **Трассировка:** возможность добавления распределённой трассировки (в перспективе — OpenTelemetry).

## 9. Требования к развёртыванию

- **Контейнеризация:** все компоненты системы (backend, frontend, БД) должны развёртываться в Docker-контейнерах.
- **Оркестрация:** инфраструктура БД поднимается через Docker Compose одной командой.
- **Конфигурация:** параметры подключения к БД выносятся в переменные окружения, не хардкодятся в коде.
- **Воспроизводимость:** развёртывание на новой машине должно занимать не более 30 минут (при наличии Docker и доступа к интернету).
- **Обновление:** обновление backend и frontend без остановки кластера БД.

## 10. Требования к документированию

- **Документация API:** автоматически генерируется через Swagger UI, доступна по адресу `/swagger-ui.html`.
- **Проектная документация:** хранится в репозитории в папке `docs/` в формате Markdown.
- **README:** в корне проекта — краткое описание, инструкция по запуску, структура проекта.
- **Диаграммы:** ER-диаграмма, Use Case, BPMN, архитектурная схема — хранятся в `docs/images/` в форматах PNG и SVG.
- **Руководство пользователя:** описывает работу с системой для каждой роли (в перспективе).

## 11. Ограничения и допущения

- **Ограничения:**
  - Система не претендует на замену полноценных ERP- или EAM-решений корпоративного уровня (SAP EAM, IBM Maximo).
  - Реализуется только веб-интерфейс (без мобильного приложения).
  - Интеграция с внешними системами ограничена одной реализуемой интеграцией (сервис мониторинга).
- **Допущения:**
  - На предприятии есть локальная сеть, в которой разворачивается система.
  - Пользователи имеют базовые навыки работы с веб-приложениями.
  - Серверная инфраструктура поддерживает Docker и Docker Compose.
  - Для работы системы не требуется специализированное оборудование (достаточно стандартного сервера).

## 12. Критерии приёмки

Система считается соответствующей нефункциональным требованиям, если:

- Все ключевые сценарии выполняются за время, указанное в разделе «Производительность».
- При остановке одного из узлов кластера БД система продолжает работать без ручного вмешательства.
- Все административные эндпоинты защищены аутентификацией и авторизацией.
- Система разворачивается на чистой машине одной командой `docker compose up -d`.
- Документация API доступна и актуальна.
- Интерфейс корректно отображается во всех поддерживаемых браузерах.
