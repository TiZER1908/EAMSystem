# Варианты использования (Use Cases)

Документ описывает варианты использования EAM-системы в соответствии с шаблоном: название, актор, участники, описание, основной сценарий, альтернативные сценарии, предусловия, постусловия, функции участников.

Каждый вариант использования идентифицируется кодом `UC-[НОМЕР]`.

## Обозначения

| Код | Вариант использования | Актор |

| UC-01 | Аутентификация пользователя | Любой пользователь |

| UC-09 | Управление пользователями | Администратор |
| UC-10 | Формирование отчёта по загрузке механиков | Мастер / Администратор |
| UC-11 | Просмотр состояния кластера БД | Администратор |

## UC-01. Аутентификация пользователя

**Вариант использования:** Аутентификация пользователя в системе

**Актор:** Любой пользователь (Администратор, Мастер, Механик, Заявитель)

**Участники:** —

**Описание:** Процесс входа пользователя в систему по логину и паролю с получением JWT-токена для доступа к защищённым разделам.

**Основной сценарий:**

1. Пользователь открывает страницу входа.
2. Пользователь вводит логин и пароль.
3. Система проверяет учётные данные.
4. Система генерирует JWT-токен и возвращает его клиенту.
5. Система сохраняет токен в локальном хранилище браузера.
6. Система перенаправляет пользователя на дашборд.

**Альтернативные сценарии:**

- А3.1: При неверном логине или пароле система отображает сообщение «Неверный логин или пароль» и предлагает повторить ввод.
- А3.2: При заблокированной учётной записи система отображает сообщение «Учётная запись заблокирована. Обратитесь к администратору».
- А3.3: При превышении лимита неудачных попыток входа система временно блокирует возможность входа.

**Предусловия:**

- Пользователь имеет учётную запись в системе.
- Учётная запись активна (не заблокирована).

**Постусловия:**

- Пользователь авторизован в системе.
- JWT-токен сохранён на клиенте.
- Пользователь перенаправлен на дашборд, соответствующий его роли.

**Функции участников в системе:**

- *Пользователь (актор):*
  - Ввод логина и пароля.
  - Подтверждение входа.
- *Система:*
  - Проверка учётных данных.
  - Генерация и выдача JWT-токена.
  - Перенаправление на дашборд.

## UC-02. Подача заявки на ремонт

**Вариант использования:** Подача заявки на ремонт оборудования

**Актор:** Заявитель (любой сотрудник предприятия)

**Участники:** Мастер (получает уведомление о новой заявке)

**Описание:** Процесс создания заявки на ремонт оборудования с указанием проблемы, приоритета и прикреплением фото. Заявка поступает в очередь на рассмотрение мастером.

**Основной сценарий:**

1. Заявитель открывает раздел «Заявки» и нажимает «Создать заявку».
2. Система отображает форму создания заявки.
3. Заявитель выбирает оборудование из списка доступных активов.
4. Заявитель вводит описание проблемы.
5. Заявитель выбирает приоритет (низкий, обычный, высокий, критичный).
6. Заявитель прикрепляет фото проблемы (опционально, до 5 изображений).
7. Заявитель нажимает «Отправить».
8. Система валидирует данные и создаёт заявку со статусом «Новая».
9. Система отправляет уведомление Мастеру о новой заявке.
10. Система отображает заявителю сообщение об успешном создании заявки.

**Альтернативные сценарии:**

- А3.1: При отсутствии оборудования в списке заявитель может создать запрос на добавление актива (в перспективе).
- А8.1: При невалидных данных (пустое описание, не выбран приоритет) система подсвечивает ошибки и не создаёт заявку.
- А8.2: При превышении лимита вложений (более 5 изображений) система отклоняет загрузку и отображает сообщение.

**Предусловия:**

- Заявитель авторизован в системе.
- Оборудование, по которому подаётся заявка, зарегистрировано в системе.

**Постусловия:**

- Заявка создана со статусом «Новая».
- Заявка отображается в списке заявок автора.
- Мастер получил уведомление о новой заявке.
- Запись о создании заявки добавлена в журнал аудита.

**Функции участников в системе:**

- *Заявитель (актор):*
  - Открытие формы создания заявки.
  - Выбор оборудования.
  - Ввод описания проблемы.
  - Выбор приоритета.
  - Прикрепление изображений.
  - Отправка заявки.
- *Мастер (участник):*
  - Получение уведомления о новой заявке.
- *Система:*
  - Валидация данных.
  - Создание заявки.
  - Отправка уведомления.
  - Запись в журнал аудита.

## UC-03. Обработка заявки мастером

**Вариант использования:** Обработка заявки на ремонт

**Актор:** Мастер

**Участники:** Заявитель (получает уведомление об изменении статуса), Механик (назначается исполнителем)

**Описание:** Процесс рассмотрения заявки мастером: принятие в работу или отклонение с указанием причины. При принятии мастер назначает исполнителя и создаёт наряд.

**Основной сценарий:**

1. Мастер открывает список заявок со статусом «Новая».
2. Мастер выбирает заявку и открывает её детали.
3. Мастер анализирует описание проблемы и приоритет.
4. Мастер нажимает «Принять в работу».
5. Система изменяет статус заявки на «Принята».
6. Система отправляет уведомление заявителю об изменении статуса.
7. Мастер создаёт наряд на основе заявки (см. UC-04).

**Альтернативные сценарии:**

- А4.1: При недостаточной информации мастер добавляет комментарий с уточняющим вопросом; заявка остаётся в статусе «Новая».
- А4.2: Мастер отклоняет заявку с обязательным указанием причины. Система изменяет статус на «Отклонена» и уведомляет заявителя.
- А4.3: При дублировании заявки мастер отклоняет её с причиной «Дубликат».
- А4.4: Мастер изменяет приоритет заявки (например, с «Обычный» на «Высокий») перед принятием.

**Предусловия:**

- Мастер авторизован в системе.
- Имеется хотя бы одна заявка со статусом «Новая».

**Постусловия:**

- Заявка переведена в статус «Принята» или «Отклонена».
- Заявитель уведомлён об изменении статуса.
- При принятии — создан наряд (или начат процесс создания наряда).
- Запись об изменении статуса добавлена в журнал аудита.

**Функции участников в системе:**

- *Мастер (актор):*
  - Просмотр списка новых заявок.
  - Открытие деталей заявки.
  - Изменение приоритета.
  - Принятие заявки в работу.
  - Отклонение заявки с причиной.
  - Добавление комментариев.
- *Заявитель (участник):*
  - Получение уведомления.
- *Механик (участник):*
  - Назначается исполнителем наряда (в рамках UC-04).
- *Система:*
  - Изменение статуса заявки.
  - Отправка уведомлений.
  - Запись в журнал аудита.

## UC-04. Создание наряда на ремонт

**Вариант использования:** Создание наряда на ремонт

**Актор:** Мастер

**Участники:** Механик (назначается исполнителем), Заявитель (уведомляется о создании наряда)

**Описание:** Процесс создания наряда на основе принятой заявки или плана ППР. Мастер назначает исполнителя, указывает сроки, перечень работ и запланированные запчасти.

**Основной сценарий:**

1. Мастер открывает раздел «Наряды» и нажимает «Создать наряд».
2. Система предлагает выбрать основание: «На основе заявки» или «На основе плана ППР».
3. Мастер выбирает «На основе заявки» и указывает принятую заявку.
4. Система заполняет данные наряда из заявки (оборудование, описание).
5. Мастер выбирает исполнителя из списка механиков.
6. Мастер указывает плановую дату начала и окончания.
7. Мастер добавляет перечень работ с указанием наименования и объёма.
8. Мастер добавляет запланированные запчасти с указанием количества.
9. Мастер нажимает «Создать».
10. Система создаёт наряд со статусом «Назначен».
11. Система отправляет уведомление механику о назначении.
12. Система отправляет уведомление заявителю о создании наряда.

**Альтернативные сценарии:**

- А2.1: Мастер выбирает «На основе плана ППР». Система не привязывает наряд к заявке, мастер вручную указывает оборудование и работы.
- А5.1: При отсутствии свободных механиков мастер сохраняет наряд как черновик и назначает исполнителя позже.
- А7.1: При необходимости мастер добавляет работы позже (до начала выполнения).
- А9.1: При невалидных данных (не указан исполнитель, сроки, работы) система подсвечивает ошибки и не создаёт наряд.

**Предусловия:**

- Мастер авторизован в системе.
- Имеется принятая заявка (для сценария «На основе заявки») или план ППР (для сценария «На основе ППР»).
- В системе зарегистрированы механики.

**Постусловия:**

- Наряд создан со статусом «Назначен».
- Механик получил уведомление о назначении.
- Заявитель уведомлён о создании наряда.
- Запись о создании наряда добавлена в журнал аудита.

**Функции участников в системе:**

- *Мастер (актор):*
  - Выбор основания для наряда.
  - Назначение исполнителя.
  - Указание сроков.
  - Добавление работ.
  - Добавление запчастей.
  - Создание наряда.
- *Механик (участник):*
  - Получение уведомления о назначении.
- *Заявитель (участник):*
  - Получение уведомления о создании наряда.
- *Система:*
  - Создание наряда.
  - Отправка уведомлений.
  - Запись в журнал аудита.

## UC-05. Выполнение наряда механиком

**Вариант использования:** Выполнение наряда на ремонт

**Актор:** Механик

**Участники:** Мастер (получает уведомление о завершении), Заявитель (получает уведомление о завершении)

**Описание:** Процесс выполнения наряда механиком: перевод в статус «В работе», отметка выполненных работ, указание фактически использованных запчастей, прикрепление фотоотчёта, отметка завершения.

**Основной сценарий:**

1. Механик открывает список назначенных ему нарядов.
2. Механик выбирает наряд и открывает его детали.
3. Механик нажимает «Начать выполнение».
4. Система переводит наряд в статус «В работе».
5. Механик выполняет работы и отмечает каждую выполненную работу в перечне.
6. Механик указывает фактически использованные запчасти и их количество.
7. Механик добавляет комментарии о ходе работ (опционально).
8. Механик прикрепляет фотоотчёт (опционально, до 5 изображений).
9. Механик нажимает «Завершить наряд».
10. Система переводит наряд в статус «Выполнен».
11. Система отправляет уведомление мастеру о завершении наряда.
12. Система отправляет уведомление заявителю о завершении работ.

**Альтернативные сценарии:**

- А3.1: При необходимости механик возвращает наряд в статус «Назначен» (если работы ещё не начаты).
- А6.1: При обнаружении дополнительных работ механик добавляет комментарий с описанием; мастер принимает решение о создании дополнительного наряда.
- А6.2: При отсутствии запчасти на складе механик указывает это в комментарии; мастер принимает решение о закупке.
- А9.1: При неполном заполнении (не отмечены все работы, не указаны запчасти) система подсвечивает ошибки и не завершает наряд.
- А9.2: При необходимости механик сохраняет наряд как черновик и завершает позже.

**Предусловия:**

- Механик авторизован в системе.
- Наряд назначен на механика и находится в статусе «Назначен» или «В работе».
- Оборудование доступно для ремонта.

**Постусловия:**

- Наряд переведён в статус «Выполнен».
- Мастер уведомлён о завершении наряда.
- Заявитель уведомлён о завершении работ.
- Фактически использованные запчасти списаны со склада.
- Запись о выполнении наряда добавлена в историю оборудования.
- Запись о выполнении наряда добавлена в журнал аудита.

**Функции участников в системе:**

- *Механик (актор):*
  - Просмотр списка своих нарядов.
  - Перевод наряда в статус «В работе».
  - Отметка выполненных работ.
  - Указание фактически использованных запчастей.
  - Добавление комментариев.
  - Прикрепление фотоотчёта.
  - Завершение наряда.
- *Мастер (участник):*
  - Получение уведомления о завершении.
  - Закрытие наряда (см. UC-06).
- *Заявитель (участник):*
  - Получение уведомления о завершении работ.
- *Система:*
  - Изменение статуса наряда.
  - Списание запчастей.
  - Отправка уведомлений.
  - Запись в историю оборудования и журнал аудита.

## UC-06. Закрытие наряда

**Вариант использования:** Закрытие наряда на ремонт

**Актор:** Мастер

**Участники:** Механик (исполнитель), Заявитель (получает уведомление о закрытии)

**Описание:** Процесс закрытия наряда мастером после подтверждения выполнения работ механиком. Наряд переводится в статус «Закрыт», данные фиксируются в истории оборудования.

**Основной сценарий:**

1. Мастер открывает список нарядов со статусом «Выполнен».
2. Мастер выбирает наряд и открывает его детали.
3. Мастер проверяет отмеченные работы, использованные запчасти и фотоотчёт.
4. Мастер нажимает «Закрыть наряд».
5. Система переводит наряд в статус «Закрыт».
6. Система фиксирует данные в истории оборудования.
7. Система отправляет уведомление заявителю о закрытии наряда.
8. Система отправляет уведомление механику о закрытии наряда.

**Альтернативные сценарии:**

- А3.1: При обнаружении несоответствий (не все работы выполнены, неверно указаны запчасти) мастер возвращает наряд механику с комментарием. Наряд переходит в статус «В работе».
- А3.2: При необходимости мастер добавляет комментарий к наряду перед закрытием.
- А4.1: При необходимости мастер отменяет наряд с обязательным указанием причины. Наряд переходит в статус «Отменён».

**Предусловия:**

- Мастер авторизован в системе.
- Наряд находится в статусе «Выполнен».
- Механик отметил завершение работ.

**Постусловия:**

- Наряд переведён в статус «Закрыт».
- Данные о наряде зафиксированы в истории оборудования.
- Заявитель и механик уведомлены о закрытии.
- Запись о закрытии наряда добавлена в журнал аудита.

**Функции участников в системе:**

- *Мастер (актор):*
  - Просмотр выполненных нарядов.
  - Проверка данных наряда.
  - Закрытие наряда.
  - Возврат наряда на доработку.
  - Отмена наряда с причиной.
- *Механик (участник):*
  - Получение уведомления о закрытии или возврате.
- *Заявитель (участник):*
  - Получение уведомления о закрытии.
- *Система:*
  - Изменение статуса наряда.
  - Фиксация в истории оборудования.
  - Отправка уведомлений.
  - Запись в журнал аудита.

## UC-07. Создание карточки оборудования

**Вариант использования:** Создание карточки оборудования

**Актор:** Мастер (или Администратор)

**Участники:** —

**Описание:** Процесс создания карточки нового оборудования с указанием инвентарного номера, наименования, типа, модели, даты ввода, местоположения и ответственного.

**Основной сценарий:**

1. Мастер открывает раздел «Активы» и нажимает «Создать актив».
2. Система отображает форму создания карточки.
3. Мастер вводит инвентарный номер.
4. Мастер вводит наименование.
5. Мастер выбирает тип оборудования из справочника.
6. Мастер вводит модель.
7. Мастер указывает дату ввода в эксплуатацию.
8. Мастер выбирает локацию из справочника (цех, участок, помещение).
9. Мастер выбирает ответственного сотрудника.
10. Мастер нажимает «Сохранить».
11. Система валидирует данные и создаёт карточку актива.
12. Система присваивает активу статус «В работе».

**Альтернативные сценарии:**

- А3.1: При дублировании инвентарного номера система отображает ошибку и не создаёт карточку.

**Вариант использования:** Управление пользователями системы

**Актор:** Администратор

**Основной сценарий (создание пользователя):**

1. Администратор открывает раздел «Пользователи» и нажимает «Создать пользователя».
2. Система отображает форму создания.
3. Администратор вводит логин, email, ФИО.
4. Администратор выбирает роль (Администратор, Мастер, Механик, Заявитель).
5. Администратор нажимает «Сохранить».
6. Система валидирует данные и создаёт учётную запись.
7. Система генерирует временный пароль.
8. Система отображает временный пароль администратору для передачи пользователю.

- А6.3: Администратор блокирует учётную запись (без удаления).
- А6.4: Администратор разблокирует учётную запись.
- А6.5: Администратор сбрасывает пароль пользователя с генерацией нового временного пароля.
- А6.6: При попытке удалить или изменить роль собственной учётной записи система отображает запрет.

**Предусловия:**

- Администратор авторизован в системе.
- Администратор имеет права на управление пользователями.

**Постусловия:**

- Учётная запись создана / изменена / заблокирована / разблокирована.
- Пользователь получил учётные данные (при создании).
- Запись о действии добавлена в журнал аудита.

**Функции участников в системе:**

- *Администратор (актор):*
  - Создание пользователя.
  - Редактирование данных.
  - Назначение и изменение роли.
  - Блокировка и разблокировка.
  - Сброс пароля.
  - Поиск пользователей.
- *Новый пользователь (участник):*
  - Получение учётных данных.
- *Система:*
  - Валидация данных.
  - Создание / изменение учётной записи.
  - Генерация временного пароля.
  - Запись в журнал аудита.

## UC-11. Просмотр состояния кластера БД

**Вариант использования:** Просмотр состояния кластера БД

**Актор:** Администратор

**Участники:** Сервис мониторинга (внешняя система, курсовая работа)

**Описание:** Процесс просмотра состояния отказоустойчивого кластера PostgreSQL: кто лидер, кто реплики, лаг репликации, события failover. Данные поступают от внешнего сервиса мониторинга, который опрашивает EAM-систему и Patroni REST API.

**Основной сценарий:**

1. Администратор открывает раздел «Мониторинг».
2. Система запрашивает данные у сервиса мониторинга.
3. Сервис мониторинга возвращает текущее состояние кластера.
4. Система отображает:
   - текущего лидера;
   - список реплик и их состояние;
   - лаг репликации;
   - статус HAProxy;
   - последние события (failover, аномалии).
5. Администратор просматривает данные.

**Альтернативные сценарии:**

- А2.1: При недоступности сервиса мониторинга система отображает сообщение «Сервис мониторинга недоступен» и данные последнего успешного опроса (если есть кэш).
- А4.1: При обнаружении аномалии (например, лаг репликации выше порога) система подсвечивает соответствующий показатель красным.
- А4.2: При наличии активных алертов система отображает их в отдельном блоке.

**Предусловия:**

- Администратор авторизован в системе.
- Сервис мониторинга запущен и доступен.
- Настроена интеграция между EAM-системой и сервисом мониторинга.

**Постусловия:**

- Администратор ознакомлен с состоянием кластера.
- Данные не изменяются.

**Функции участников в системе:**

- *Администратор (актор):*
  - Открытие раздела «Мониторинг».
  - Просмотр данных.
- *Сервис мониторинга (участник):*
  - Предоставление данных о состоянии кластера.
- *Система:*
  - Запрос данных у сервиса мониторинга.
  - Отображение данных.
  - Подсветка аномалий.
